Overview

A week of trying to build a streaming-analytics library that wins on the tail-latency axis where heapq and Redis lose, without giving up the ergonomics that make those tools popular. I ended up with four primitives (Top-K, heavy hitters, distinct count, set membership), a Python API with two backends, a Rust crate, an Apache Arrow bridge into any SQL engine, and a single-binary HTTP dashboard. None of the algorithms are novel — every primitive has a 1980s–2010s paper behind it. The interesting work is the composition: noticing that mergeable summaries is a single property that simultaneously gives you persistence, distribution, and time-window rollups for free, and that Apache Arrow is the right boundary between a streaming primitive and a SQL engine — so you don't have to write your own query language.

The Brief

"Take the lock-free streaming-analytics code that we have and turn it into a real product. Beat std::priority_queue and std::unordered_set in HFT-style hot paths. Keep p99.99 in nanoseconds. Pure C++17. Ship it with bindings, ship it with benchmarks against the obvious alternatives, ship it with honest documentation about what's borrowed math vs what's engineering."

Development Journey

v0.1 → v0.2 — Production hardening

The handoff code worked but was a sketch. I added:

  • An mmap-backed arena allocator so the Galois filter can be loaded from a file with zero copy, and shared across processes via MAP_SHARED.
  • A C ABI so Python and Rust can bind without writing C++.
  • A ctypes-based Python package with numpy zero-copy bulk ingest.
  • CMake, unit tests, a microbench, and a global merger thread that periodically aggregates per-shard Top-Ks into a final snapshot.

v0.3 — The math actually works

Replaced the lossy placer with a real two-step Gaussian-elimination Cuckoo builder:

  • Two-choice load balancing: each key has two candidate blocks (h1, h2); assign it to whichever is less loaded. Standard power-of-two-choices result.
  • Per-block GF(2) solve: for each block, set up the linear system V · P_j = F_j over 8 right-hand sides at once (share the elimination across columns). Solve via standard row reduction. If inconsistent, increment the seed and retry. 256 seeds is enough that build failure probability is astronomically small.

Also shipped: AVX-512 VPOPCNTDQ filter path (compile-time gated), SSTable format with magic+version header, Rust crate.

v0.4 — See it run

Wanted a way to demo the engine without making people read a Python script. Built a single-binary HTTP/1.1 + SSE server in ~400 lines of C++ (hand-rolled parser, no httplib, no Boost). Endpoints: /, /topk, /ingest, /stream, /metrics, /healthz. Browser dashboard in vanilla JS with no build step.

The SSE stream is delta-encoded — every tick, the server diffs the current sorted Top-K against the previous one and emits only the items that entered or exited. Steady-state bandwidth is ~30 bytes per event. Side effect: the rate of delta events itself doubles as a distribution-drift signal.

v0.5 — heapq is shockingly fast (and a real bug)

Wrote an honest side-by-side benchmark against the canonical Python solution (heapq.heappush + set). Expected Stratum to win comfortably. It didn't, for two reasons:

  • heapq is C-implemented under a Python for loop. The inner loop is tight, allocations are amortized, GC barely triggers. At small/medium scale it's hard to beat by more than a small constant.
  • 17/100 correctness mismatch. The AsyncTopK keeps a partial "active" buffer and only flushes to the merger when the buffer fills. With a finite stream that ends mid-buffer, the last ~few-hundred events per shard never reach the merger. Some of those were the actual top values.

Fixes: added a request_flush() flag, and built a dual-backend pattern instead — same Python API, two implementations: numpy.argpartition backend wins ~16× over heapq for one-shot bulk; native backend keeps the 5.94 ns story for per-event streaming.

v0.6 — Mergeable summaries (one math idea, three properties)

Noticed the same idea solves three separate problems: mergeable summaries. A summary S is mergeable iff there exists a deterministic associative commutative ⊕ such that:

S(stream_a) ⊕ S(stream_b) == S(stream_a ++ stream_b)

When your primitive is mergeable, three operational properties fall out for free:

  • Persistence without a write-ahead log. snapshot = save(summary) on a cadence you pick. Recovery = merge(load(snapshot), in_memory). Loss bound: bounded by the gap between snapshots.
  • Distributed views without consensus. Each node builds its own summary. Periodically gossip and merge. The global view is exact without Raft or Paxos.
  • Time-window rollups without rescanning. Build one summary per minute. The summary for an hour is the merge of 60 of them.

Shipped Misra-Gries (1982) for frequency-tracking — four pages, beats most modern sketches, mergeable, ~10 ns per add via open-addressing hash table.

v0.7 — The SQL bridge (without writing a query engine)

The wrong answer: build a query engine inside Stratum. The right answer: make the primitives queryable by every SQL engine that already exists via Apache Arrow.

import duckdb, stratum
hh = stratum.HeavyHitters(k=32, backend="native")
hh.add_many(user_ids)
con = duckdb.connect()
stratum.sql.register(con, "hh", hh)
con.sql("""
    SELECT h.key, h.count, u.name, u.status
    FROM hh h LEFT JOIN users u ON h.key = u.id
    ORDER BY h.count DESC LIMIT 10
""")

Also shipped: HyperLogLog (Flajolet 2007, Heule 2013) as another mergeable primitive. Maps to SQL's COUNT(DISTINCT) at 16 KB of state.

What I Learned

The cross-disciplinary borrow that worked

The most useful insight wasn't a clever algorithm — it was noticing that "mergeable summary" from streaming-algorithms, "CRDT" from distributed-systems, and "commutative monoid" from algebra are all the same thing. Once I saw it, three operational properties collapsed into one property.

Don't fight the FFI boundary

I lost hours assuming Stratum's native backend had to win on raw throughput vs heapq at every scale. It doesn't, and shouldn't. Python→C FFI has ~600 ns of overhead per call. The right move was to admit it, build a parallel pure-Python backend that uses numpy.argpartition, and reserve the native backend for streams that actually care about per-event tail latency.

The bug that took an hour

The 17/100 correctness mismatch was the most embarrassing moment of the week. The pipeline had been "working" for days; what had actually been working was the throughput. Lesson: every streaming primitive needs a single test where it has to match a known-correct reference on the same input. End-of-stream behavior is the most common bug.

Composition beats invention

None of the four primitives shipped here are new. The interesting work was making them fit: same architectural shape, same API surface, same dual backend, same Arrow representation. The fit is the product.

What I Will NOT Claim

  • None of the algorithms are novel. EVT-membrane Top-K, Galois bipartite filter, Misra-Gries, and HyperLogLog all have 1980s–2010s papers.
  • All numbers are Apple M-series. The AVX-512 VPOPCNTDQ filter path compiles but I have not measured it on real hardware.
  • Streaming add() from Python is FFI-bound, not nanosecond. The 0.26 ns and 5.94 ns numbers are the C-side hot path. From Python, per-call overhead is ~600 ns; use add_many with chunks of 1k+.
  • This is not a database. No transactions, no streaming joins, no late-data handling, no SQL of its own.
  • Persistence is bounded-loss, not durable. Loses at most the events between the last snapshot and the crash.
  • This took a week of wall-clock — heavily AI-assisted (Claude wrote most of the C++ under my direction). It is what one person + a strong LLM can produce when the problem decomposes cleanly into small primitives.
