Overview

A week of trying to build a streaming-analytics library that wins on the tail-latency axis where heapq and Redis lose, without giving up the ergonomics that make those tools popular. I ended up with four primitives (Top-K, heavy hitters, distinct count, set membership), a Python API with two backends, a Rust crate, an Apache Arrow bridge into any SQL engine, and a single-binary HTTP dashboard. None of the algorithms are novel — every primitive has a 1980s–2010s paper behind it. The interesting work is the composition: noticing that mergeable summaries is a single property that simultaneously gives you persistence, distribution, and time-window rollups for free, and that Apache Arrow is the right boundary between a streaming primitive and a SQL engine — so you don't have to write your own query language.

The Brief

"Take the lock-free streaming-analytics code that we have and turn it into a real product. Beat std::priority_queue and std::unordered_set in HFT-style hot paths. Keep p99.99 in nanoseconds. Pure C++17. Ship it with bindings, ship it with benchmarks against the obvious alternatives, ship it with honest documentation about what's borrowed math vs what's engineering."

Development Journey

v0.1 → v0.2 — Production hardening

The handoff code worked but was a sketch. I added: mmap-backed arena allocator, C ABI for Python/Rust bindings, ctypes-based Python package with numpy zero-copy bulk ingest, CMake/tests/microbench, and a global merger thread for shard aggregation.

v0.3 — The math actually works

Replaced the lossy placer with a real two-step Gaussian-elimination Cuckoo builder with two-choice load balancing and per-block GF(2) solve. Also shipped: AVX-512 VPOPCNTDQ filter path, SSTable format with magic+version header, Rust crate.

v0.4 — See it run

Built a single-binary HTTP/1.1 + SSE server in ~400 lines of C++ (hand-rolled parser, no httplib, no Boost) with browser dashboard in vanilla JS.

v0.5 — heapq is shockingly fast (and a real bug)

Wrote honest side-by-side benchmark. Found 17/100 correctness mismatch and realized heapq's C implementation is genuinely hard to beat. Built dual-backend pattern: numpy.argpartition backend wins ~16× for bulk operations; native backend keeps 5.94 ns story for per-event streaming.

v0.6 — Mergeable summaries (one math idea, three properties)

Noticed the same idea solves three separate problems: persistence without write-ahead log, distributed views without consensus, time-window rollups without rescanning. Shipped Misra-Gries (1982) for frequency-tracking. Also shipped: HyperLogLog for cardinality at 16 KB state.

v0.7 — The SQL bridge (without writing a query engine)

Made primitives queryable by existing SQL engines via Apache Arrow. Now any modern analytics engine (DuckDB, Polars, DataFusion, ClickHouse, Velox) can accept Arrow tables as virtual tables in zero-copy.

What I Learned

The cross-disciplinary borrow that worked: Noticing that "mergeable summary" from streaming-algorithms, "CRDT" from distributed-systems, and "commutative monoid" from algebra are all the same thing. Once I saw it, three operational properties collapsed into one property.

Don't fight the FFI boundary: Python→C FFI has ~600 ns of overhead per call. The right move was to admit it, build a parallel pure-Python backend that uses numpy.argpartition, and reserve the native backend for streams that actually care about per-event tail latency.

The bug that took an hour: The 17/100 correctness mismatch was the most embarrassing moment. The pipeline had been "working" for days; what had actually been working was the throughput. Lesson: every streaming primitive needs a single test where it has to match a known-correct reference.

Composition beats invention: None of the four primitives are new. The interesting work was making them fit: same architectural shape, same API surface, same dual backend, same Arrow representation. The fit is the product.
