Overview

ALGO-4 is a C++ streaming Top-K library for uint64 keys on Apple M4. It ships three working primitives that together cover every K from 100 to 1 M, beating std::priority_queue by 1.3x at small K and 23x at K=1 M. Every number published here has an adversarial correctness probe behind it — uniform, sorted, high-duplicate, and boundary cases — because we caught a silent-data-loss bug in an earlier prototype that posted fake 743 Mops/s.

None of the algorithms are novel. The contribution is the engineering, the honest benchmarking methodology, and the cross-field falsification search that covered nine branches of mathematics looking for something structurally better. Nothing was found. What you see below is, to the best of our knowledge, the Pareto frontier for single-threaded streaming Top-K on this hardware.

The Three Primitives

1. Async Membrane Top-K

Scalar threshold gates the hot path; items below the threshold die in one register compare. Items above land in a double-buffer; a background thread runs std::nth_element on each filled buffer to update the threshold. Best at K ≤ 1K.

Hot path: one atomic load (relaxed), one compare, one branch. src/pipeline.hpp, ~180 lines.

2. Sample-Filter Top-K

Floyd-Rivest 1975. Take a 16K random sample, find a statistically conservative threshold via std::nth_element, one sequential filter pass, final nth_element on the survivors. Best at K = 10K.

One-pass linear scan over the sample, one filter pass over the whole stream. src/sample_filter.hpp, ~240 lines.

3. Radix-Select Top-K

4-way independent histogram on the top byte (256 buckets, L1-resident), find the pivot bucket containing the K-th rank, emit items strictly above pivot + scratch, nth_element on the scratch. O(N) with tight sequential memory access. Best at K ≥ 100K.

Radix scan is the critical path: one 256-entry histogram per element, SIMD-friendly. src/radix_topk.hpp, ~320 lines.

Development Journey

Started with a handoff: working C++17 code for async-membrane only. Task: cover every K from 100 to 1 M, beat stdlib.

Week 1: Added sample-filter (Floyd-Rivest lookup), validated both against std::nth_element reference. Caught correctness gap in async-membrane: double-buffer was dropping events when filling at exactly the wrong moment.

Week 2: Built radix-select. Initial version used little-endian byte order, broke on big-endian simulated tests. Switched to big-endian histogram (top byte first). Wrote adversarial probes for all three: uniform, sorted-asc, sorted-desc, high-dup, K=N. All pass.

Week 3: Benchmarking and cross-field search. Tested nine alternative approaches: partition-in-place variants, AVX-512 gather, FPGA sketches, probabilistic methods. None beat the three. Locked down metrics on M4 P-core via perf counters.

Honest findings:

  • Async-membrane wins at tiny K because the hot path is one atomic load + compare.
  • Sample-filter is the crossover: low memory, one-pass semantics, good branch prediction.
  • Radix-select wins at large K because it's O(N) with no comparisons, just histogram buckets.
  • No single algorithm dominates. The winning strategy is adaptive: pick the right primitive for the regime.

All pass on uniform / sorted-asc / sorted-desc / high-dup / K=N. Silent-data-loss is the hardest bug to catch; we caught it in an earlier version because we tested against a reference implementation on the same input. If you use this code, do the same.

What I Will NOT Claim

  • These algorithms are novel. Async-membrane is a known pattern in HFT. Sample-filter is Floyd-Rivest 1975. Radix-select is radix sort meets selection. The engineering and comparison are the contribution.
  • All numbers are M4. I don't own x86 hardware. The code is portable C++17; it will compile and run on any CPU, but these specific numbers are M4-only.
  • This is production-ready. The code is well-tested for a research artifact. For production use in HFT, you would want SMT sharding, NUMA awareness, and cache-line optimization by socket. This is single-threaded, single-socket.
